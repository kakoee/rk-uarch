## Interfaces and behavior

Existing `component::execute(input, trust)` remains the /2 entry point. New internal `execute_with_observations(input, trust, ObservationVersion::{V2,V3})` binds V2 to native-intervals model version1 and V3 to model version2. There is no public selector, input flag or Python-prevalidation flag. The public protocol module is unchanged. Native `validate` retains the old schema; typed `validate_model(..., ModelVersion::Two)` uses the separately compiled `component_carriers_v3.json`. A model2 input is rejected by the original /2 seam; the new seam rejects model1 at the strict proposed schema.

For /3, every DMA request prepends a core-domain, memory-category, nonoccupied `dma_issue` alignment and zero-duration service owned by its flattened DMA engine. Alignment uses TASK_READY/DEPENDENCY_READY; issue service uses TASK_READY/DMA_ISSUE. Both exist even at zero alignment. Alignment starts when the request actually reserves capacity. Service atomically changes pending reservation to acquired credit at the core edge, records issue, then permits payload phases. Existing Event/Wheel/Arena ordering and scheduled sequence IDs remain in use. Positive-duration completions dispatch at phase0 before phase2 work; zero-duration inline endpoints, including write ACK, retain the existing phase2 closure rule and precede later dependent transitions by ordinal.

The engine tracks waiting (no slot), pending reservation and acquired/inflight separately. Per engine, acquired plus pending cannot exceed its limit. Reservation grants use canonical readiness/engine/request order and do not impose another issue rate cap. Thirty-three requests can issue at the same edge when capacity permits. Pending capacity prevents two requests from claiming a cap1 slot before either issues. Separate engines have separate credit pools.

The strict credit cause rule compares **reservation time > job readiness**, not later issue time > readiness. It additionally requires saturation immediately before reservation and selects all acquired requests actually released at that time. If job readiness and release coincide, the first issue alignment has dependency causes only. Sequence and other eligible tight causes remain exact.

The proposed /3 DMA row has required `reservation_ps` (null only for unicast). Every DMA contributes exactly one row each, including zero length: `dma_waiting:E`/waiting from job readiness to reservation; `dma_pending:E`/pending from reservation to issue; existing `dma_inflight:E`/inflight from issue to completion. These ledger rows have the DMA owner and null clock/activity. Ordinary phase queue and clock rows still describe actual core alignment/service. Job start is the minimum request reservation and nonpersistent producer allocation starts then; no DMA payload phase precedes issue. /2 records do not acquire the new fields or queues.

The /3 constructor uses a conservative 28-endpoint bound per sequence because a write can now have26 endpoints; /2 retains24. A private typed capacity test with35715 fragments discriminates the new limit. This synthetic duplicate-ID capacity state is not claimed as a mapped admitted workload.
