# Construction version and installation rules

This is an additive unapplied preparation amendment. It does not change Rust model semantics, profiles, registry admission, public transport, authority or historical output selection. Exact later source/consumer manifests, not this document, bind actual postimages.

`uarch-component-build-inputs/2` remains a historical format. Its original `ComponentBuildInputs` class syntax and generated JSON schema are byte-equivalent to the accepted prior implementation; the focused synthetic parsing control preserves its serialization/content hash. The new explicit reader dispatches /2 to that original class and /3 to `ComponentBuildInputsV3`. It does not rewrite old BuildInputs, receipts, payloads or binaries. New production command rendering requires /3 and refuses /2 rather than inferring missing construction declarations.

`uarch-component-build-inputs/3` retains the existing source/tool/trust/generated-identity joins, sorted unique inventory and ordered debug/release requirements. Its `mode_configs` entries contain `mode`, the full ordered `cargo_args`, accepted `rustflags`, and the full per-mode `permitted_environment`. There is no shared top-level environment. `component_construction.mode_spec` is the sole production specification: exactly one linker-map suffix, release flag only in release, and eleven exact environment keys/values, with mode-specific C2_RUN_TAG. Every mode is validated against that specification, including the unselected mode. Missing keys, extra keys, argument omissions/duplicates, reordered or duplicate modes and wrong-mode values refuse. The schema export describes record shape; exact values/order are additionally enforced by the source-bound model validator, not by assuming JSON Schema expresses that executable check.

The future `freeze()` uses `construction_modes(tools.flags)`, checks the accepted ToolInputs flags, and writes /3 inputs. The pure `construction_recipe()` hashes those exact input bytes and copies their source commit, exact preparation-source inventory entry, complete mode entries and generated-identity paths into `component-capture-recipe/2`. It does not consult environment variables or invent a runtime identity. Synthetic records used in tests are labelled synthetic; no real input/recipe pair was generated in this work.

The production builder reads /3, validates it again before rendering, and passes the selected full argv once to the existing container-prefix code. Its old unconditional linker-map append is removed. The explicit environment argument replaces the wrapper defaults as a complete dictionary; it never merges defaults or ambient values. `/usr/bin/env -i` remains the launch prefix. The six additional keys are PATH, CARGO_REGISTRIES_CRATES_IO_PROTOCOL, RUSTC, RUSTC_WRAPPER, RUSTFLAGS and C2_RUN_TAG. Their values are the already accepted wrapper values. Historical auxiliary/tool/test-build calls using the wrapper's default environment retain their prior behavior; this amendment's production recipe does not claim those separate commands are production captures.

The capture monitor requires recipe /2 exactly with BuildInputs /3, and exact equality of the mode list and generated paths with BuildInputs. The selected plan environment must equal both its bound environment input and the selected mode's complete declaration. The unwrapped child argv must equal Cargo plus the selected complete argument vector. A recipe cannot override /3, and recipe /1 cannot be substituted for /3. Legacy /1 recipes retain their existing equality rules for earlier declarations and the separately specified canary. There is no silent fallback to legacy fields, no environment template, and no relaxed equality.

B's diagnostic proposal is separate from construction identity: the plan keeps this exact unwrapped child argv/environment while the outer command and guardian intent separately bind any diagnostic redirection wrapper. B owns raw-stream attribution, classification, limits and conservative diagnostic refusal. The proposed policy is not human approval; real expected diagnostic lines cannot be inferred from synthetic anchors. The final combined patch uses B ac9c5f6 bytes and e964215 evidence, with import-order-only monitor cleanup, and keeps all these construction equalities. The additive startup project-copy correction includes all three documentation-hosted helper inputs; it does not invoke startup or replace an immutable manifest.

Installation order is acyclic: review actual A/B source postimages and the full/additive patches; freeze the selected tool's binding path; hash that tool and all actual source/consumer inputs into an additive binding; hash the full prospective source inventory and package manifest; obtain the required review/installation decisions. Only a later separately authorized construction may create new BuildInputs/generated identity/engine/binaries/receipts/payload. Those identities must derive from the actually installed/frozen bytes, including the new specification, typed reader, wrapper, monitor and diagnostic closure. Old binaries cannot be rebound. The changed schema reader is data admission only and creates no HostRecord, selector, profile authority or successful public job.

Protected ADR/default-route/D3 changes remain unapplied. A-F3 is deferred; the stopped startup-substitution/defense-revert activity was not retried, reconstructed or transferred. All three read gaps, incident impact, genuine human L1, /2 first-use restrictions, U0024 and separate deployment/authority/public-execution decisions remain unchanged. No new dependency, toolchain/licence vote, build, Docker exercise, tracing, campaign, placement or closure is part of this amendment.
